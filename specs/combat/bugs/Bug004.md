# Bug Correction — Duplicate Combat Event Avalanche / Invalid UnitDied Emission

## Objetivo

Corrigir um bug na simulação de combate event-driven em que uma única batalha pode produzir uma quantidade de eventos de combate incompatível com a quantidade real de unidades existentes, culminando em uma quantidade absurda de `UnitDiedEvent`.

A correção deve encontrar e eliminar a **causa arquitetural** da duplicação.

**Não implementar apenas um guard superficial em `UnitDiedEvent` para esconder o problema.**

---

## 1. Contexto arquitetural

A simulação de combate é uma **Discrete Event Simulation (DES)** determinística.

Princípios relevantes:

- Não existe tick global.
- O tempo avança conforme eventos são processados.
- A fila de eventos é centralizada no `CombatApplication`.
- Eventos são imutáveis e representam acontecimentos/processamentos da simulação.
- Módulos de domínio não conhecem diretamente a fila.
- O `CombatApplication` orquestra o processamento e o agendamento.
- O sistema utiliza versionamento para invalidar eventos antigos.
- A arquitetura segue a separação:

```text
Commands → Events → Systems / Modules → novos Events
```

A arquitetura documentada estabelece que módulos recebem eventos e podem retornar novos eventos, enquanto o `CombatApplication` é responsável pela fila e pela orquestração.

Também existe a separação conceitual:

```text
npcService pensa
unitService executa
```

O `npcService` é responsável por decisões/coordenação e o `unitService` pela execução das ações.

---

## 2. Sintoma observado

Ao inserir várias unidades simultaneamente, especialmente unidades com comportamento `AGGRESSIVE`, a simulação entra em uma espécie de **avalanche de eventos**.

O problema observado não é simplesmente:

> várias unidades atacando o mesmo alvo.

Isso é válido.

Exemplo válido:

```text
Unit A ─┐
Unit B ─┤
Unit C ─┼──→ Target X
Unit D ─┤
Unit E ─┘
```

Se `Target X` morrer, é esperado que várias unidades percam seu alvo.

O problema é outro:

```text
poucas unidades realmente spawnadas
        ↓
quantidade enorme de eventos de combate
        ↓
quantidade de DamageAppliedEvent incompatível
        ↓
quantidade de UnitDiedEvent incompatível
```

Em particular, o log apresenta grandes sequências de:

```text
AttackImpactEvent
DamageAppliedEvent
UnitDiedEvent
```

em intervalos de poucos milissegundos.

Exemplos do log mostram dezenas de `DamageAppliedEvent` e `UnitDiedEvent` consecutivos em aproximadamente 1–20 ms, e o padrão se repete em diferentes momentos da simulação.

---

## 3. Evidência importante

O log mostra sequências como:

```text
AttackImpactEvent
AttackImpactEvent
...

DamageAppliedEvent
DamageAppliedEvent
...

UnitDiedEvent
UnitDiedEvent
...
```

e posteriormente:

```text
UnitAggroStoppedEvent
TargetLostEvent
UnitAggroSearchEvent
UnitAggroIntentEvent
AggroIntentAccepted
UnitAggroStartedEvent
MovementIntent
...
```

Isso demonstra que o problema não parece ser exclusivamente visual ou de frontend.

A avalanche acontece dentro do pipeline da própria simulação.

Além disso, o cenário reproduzido envolve várias units agressivas sendo inseridas praticamente juntas.

---

## 4. Invariante fundamental

A seguinte regra deve ser preservada:

> **Uma unidade só pode realizar a transição `Alive → Dead` uma vez durante uma batalha.**

Consequentemente:

```text
UnitSpawned(X)
...
UnitDied(X)
```

deve representar uma única transição terminal.

Depois que `X` morreu:

```text
X = DEAD
```

nenhum processamento posterior deve conseguir produzir uma nova morte válida para `X`.

Portanto, não é válido ter:

```text
UnitDied(X)
UnitDied(X)
UnitDied(X)
```

como acontecimentos independentes da mesma unidade.

Também não é válido produzir mortes para unidades que já estão mortas ou que não existem no estado atual da simulação.

---

# 5. O que NÃO deve ser assumido

Não assumir que o problema é:

```text
10 unidades atacando 1 unidade
```

Isso é perfeitamente válido.

Também não assumir automaticamente que `UnitDiedEvent` é a origem.

`UnitDiedEvent` pode ser apenas o último efeito de uma cadeia duplicada.

A investigação deve encontrar **o primeiro ponto em que a cadeia causal diverge do esperado**.

---

# 6. Estratégia de investigação

## 6.1 Mapear o pipeline completo

Localizar todos os pontos que produzem/consomem:

```text
AttackIntent
AttackIntentAccepted
AttackStartedEvent
AttackResolvedEvent
AttackImpactEvent
DamageAppliedEvent
UnitDiedEvent
UnitAggroStoppedEvent
TargetLostEvent
UnitAggroSearchEvent
```

Para cada evento, identificar:

1. Quem cria o evento?
2. Quem agenda o evento?
3. Quem consome o evento?
4. Quem pode produzir o próximo evento?
5. Quantas vezes o listener/handler é registrado?
6. Existe versionamento?
7. Qual entidade/version o evento representa?

Não alterar código antes de entender esse fluxo.

---

## 6.2 Determinar onde a primeira duplicação ocorre

A investigação deve comparar as contagens:

```text
AttackIntent
AttackIntentAccepted
AttackStartedEvent
AttackResolvedEvent
AttackImpactEvent
DamageAppliedEvent
UnitDiedEvent
```

Para cada etapa, verificar se:

```text
1 entrada → 1 saída
```

quando a relação deveria ser 1:1.

Também existem relações naturalmente 1:N, por exemplo:

```text
UnitDied(X)
    ↓
TargetLost(A, X)
TargetLost(B, X)
TargetLost(C, X)
```

Isso é válido.

O que não é válido é:

```text
UnitDied(X)
UnitDied(X)
UnitDied(X)
```

para a mesma unidade.

---

# 7. Instrumentação obrigatória durante a investigação

Adicionar temporariamente informações suficientes para rastrear a causalidade dos eventos.

Sempre que possível, registrar:

```text
eventId
eventType
sourceId
targetId
entityId
version
simulationTime
```

Principalmente para:

```text
AttackStartedEvent
AttackImpactEvent
DamageAppliedEvent
UnitDiedEvent
```

O objetivo é distinguir:

### Caso A — evento criado várias vezes

```text
UnitDiedEvent #A
UnitDiedEvent #B
UnitDiedEvent #C
```

com IDs diferentes.

Isso indica múltiplas emissões.

### Caso B — mesmo evento processado várias vezes

```text
UnitDiedEvent #A
UnitDiedEvent #A
UnitDiedEvent #A
```

Isso indica problema de processamento/dispatch/fila.

### Caso C — eventos diferentes, mesma unidade

```text
UnitDiedEvent #A source=X
UnitDiedEvent #B source=X
```

Isso indica múltiplas tentativas de matar a mesma unidade.

Essa distinção é essencial antes de aplicar qualquer correção.

---

# 8. Verificar listeners e subscriptions

Como o problema aparece com múltiplas units, investigar cuidadosamente se listeners estão sendo registrados mais de uma vez.

Procurar por padrões como:

```lua
eventService:on(...)
eventService:subscribe(...)
eventService:register(...)
```

e verificar se algum registro ocorre dentro de:

```text
spawn de unit
criação de NPC
inicialização de entidade
criação de battle context
setup de unidade
```

Um listener global de combate não deve ser registrado novamente simplesmente porque uma nova unit foi criada, salvo quando essa multiplicidade for explicitamente desejada.

Verificar especialmente se:

```text
1 unit  → N listeners
2 units → N×2 listeners
10 units → N×10 listeners
```

está ocorrendo acidentalmente.

---

# 9. Verificar múltiplos consumidores

Para cada evento, garantir que o `CombatApplication` não esteja fazendo algo equivalente a:

```text
evento
 ↓
handler A
handler B
handler C
 ↓
cada handler produz o mesmo evento derivado
```

quando apenas uma aplicação deveria acontecer.

Diferenciar:

- múltiplos listeners intencionais;
- múltiplos efeitos diferentes;
- múltiplas execuções da mesma transição.

---

# 10. Verificar reentrada

Investigar ciclos causais.

Exemplo suspeito:

```text
AttackIntent
    ↓
AttackIntentAccepted
    ↓
AttackStartedEvent
    ↓
AttackImpactEvent
    ↓
DamageAppliedEvent
    ↓
UnitDiedEvent
    ↓
TargetLostEvent
    ↓
novo targeting
    ↓
AttackIntent
```

O ciclo acima pode ser válido em condições específicas.

O problema ocorre se alguma etapa fizer a mesma transição repetidamente sem que o estado tenha mudado.

Exemplo:

```text
AttackIntent(A → X)
    ↓
AttackStarted(A → X)
    ↓
AttackStarted(A → X)
    ↓
AttackStarted(A → X)
```

ou:

```text
DamageApplied(A → X)
    ↓
DamageApplied(A → X)
    ↓
DamageApplied(A → X)
```

sem que existam ataques independentes válidos.

---

# 11. Verificar estado de vida antes de gerar UnitDied

Localizar exatamente o ponto responsável pela transição de vida para morte.

A transição deve ser conceitualmente equivalente a:

```lua
if unit is already dead then
    do not perform death transition
end

if damage causes health <= 0 then
    transition Alive -> Dead
    emit UnitDiedEvent
end
```

A implementação concreta deve respeitar a arquitetura existente.

**Não introduzir uma correção isolada que apenas descarte `UnitDiedEvent` depois que ele já foi criado.**

O estado deve impedir que a transição terminal seja realizada novamente.

---

# 12. Verificar DamageAppliedEvent

A principal hipótese operacional é que múltiplos `UnitDiedEvent` podem ser apenas consequência de múltiplos danos inválidos.

Investigar:

```text
AttackImpactEvent
        ↓
DamageAppliedEvent
        ↓
health mutation
        ↓
UnitDiedEvent
```

Para cada `DamageAppliedEvent`, validar:

- atacante ainda existe?
- alvo ainda existe?
- atacante ainda está vivo?
- alvo ainda está vivo?
- evento ainda possui version válida?
- ataque ainda é válido?
- o mesmo impacto já foi processado?
- o impacto foi agendado mais de uma vez?

Um evento de impacto antigo não deve causar dano em uma unidade que já saiu do estado que tornava o impacto válido.

---

# 13. Verificar versionamento

A arquitetura utiliza versionamento para cancelar implicitamente eventos antigos.

Garantir que eventos de combate sujeitos a invalidação estejam associados ao estado/version correto da entidade.

Exemplo conceitual:

```lua
if event.version ~= entity.version then
    return
end
```

Não adicionar versionamento arbitrariamente em todos os eventos.

Primeiro determinar:

1. qual entidade o evento representa;
2. qual mudança invalida o evento;
3. qual version deve ser comparada.

Um evento de ataque/impacto antigo não deve sobreviver a uma mudança de estado que o tornou inválido.

---

# 14. Invariantes que a correção deve garantir

Após a correção:

### Vida

```text
Alive → Dead
```

somente uma vez por unit.

### Morte

Para cada `unitId`:

```text
count(UnitDiedEvent(unitId)) <= 1
```

durante uma batalha.

### Impacto

Um impacto inválido não pode produzir dano.

### Dano

Um dano inválido não pode produzir morte.

### TargetLost

Uma unidade pode perder o mesmo alvo em consequência da morte dele, mas isso não implica que o evento `UnitDied` deva ser multiplicado.

### Determinismo

A correção não pode introduzir comportamento dependente de:

- ordem de execução de callbacks externos;
- `os.clock`;
- `task.wait`;
- `Heartbeat`;
- concorrência assíncrona;
- estado não determinístico.

A simulação deve continuar determinística.

---

# 15. Teste mínimo de reprodução

Criar/reproduzir o cenário com a menor quantidade possível de units.

Começar com:

```text
1 atacante
1 alvo
```

Depois:

```text
2 atacantes
1 alvo
```

Depois:

```text
3–5 atacantes
1 alvo
```

E finalmente reproduzir o cenário original de múltiplas units agressivas.

Para cada cenário registrar:

```text
spawned units
unique spawned IDs
AttackIntent count
AttackStartedEvent count
AttackImpactEvent count
DamageAppliedEvent count
UnitDiedEvent count
unique UnitDied sourceIds
duplicated UnitDied sourceIds
```

---

# 16. Critérios de aceitação

A correção só está concluída quando:

- [ ] O cenário original deixa de produzir avalanche de eventos.
- [ ] Uma unit nunca produz mais de um `UnitDiedEvent`.
- [ ] Uma unit morta não recebe novos danos válidos.
- [ ] Impactos inválidos não geram `DamageAppliedEvent`.
- [ ] Eventos antigos são corretamente invalidados quando necessário.
- [ ] Não existem listeners duplicados acidentalmente.
- [ ] O número de eventos volta a ser compatível com o número real de unidades/ações.
- [ ] O cenário com várias units agressivas funciona normalmente.
- [ ] O cenário com várias units atacando o mesmo alvo continua funcionando.
- [ ] `TargetLostEvent` continua sendo emitido para as unidades que realmente perderam o alvo.
- [ ] A correção não depende de um debounce/timer artificial.
- [ ] A correção não simplesmente ignora `UnitDiedEvent` duplicado depois que ele foi produzido.
- [ ] A simulação continua determinística.
- [ ] Nenhuma regra de domínio existente é removida sem justificativa.

---

# 17. Restrições da implementação

## Não fazer

Não:

- adicionar debounce temporal para esconder o bug;
- adicionar `task.wait`;
- adicionar `Heartbeat`;
- criar um tick global;
- simplesmente ignorar todos os `UnitDiedEvent` após o primeiro;
- remover listeners sem entender por que existem;
- alterar a arquitetura DES;
- mover regras de domínio para `CombatApplication` apenas para fazer o bug desaparecer;
- criar estado duplicado fora do `UnitState` apenas para controlar morte;
- refatorar sistemas não relacionados ao bug.

## Fazer

Sim:

- descobrir a primeira duplicação causal;
- corrigir a origem;
- preservar as responsabilidades atuais;
- preservar determinismo;
- manter `CombatApplication` como orquestrador;
- manter módulos como responsáveis pelo domínio;
- usar o estado/versionamento existente quando apropriado;
- adicionar testes/regressões para a causa encontrada.

---

# 18. Resultado esperado

O comportamento final deve ser equivalente a:

```text
Spawn units
    ↓
Units acquire targets
    ↓
Units attack
    ↓
AttackImpact
    ↓
DamageApplied
    ↓
se health <= 0:
    Alive → Dead
    ↓
    UnitDiedEvent (UMA VEZ)
    ↓
    unidades que tinham essa unit como alvo
        ↓
        TargetLost
        ↓
        novo targeting, se aplicável
```

E nunca:

```text
DamageApplied
    ↓
UnitDied
UnitDied
UnitDied
UnitDied
...
```

sem que existam unidades distintas correspondentes a essas mortes.

---

# 19. Nota importante para a IA que implementará a correção

**Não assumir a causa antes de investigar.**

O log prova a existência de uma avalanche de eventos, mas não prova sozinho se a origem é:

- duplicação de listeners;
- múltiplas emissões;
- reentrada;
- eventos duplicados na fila;
- falta de invalidação por versionamento;
- múltiplos impactos válidos/considerados válidos;
- estado de morte não protegido;
- ou outra falha arquitetural.

A implementação deve primeiro localizar a **primeira duplicação causal** e então corrigir a origem.

A correção deve ser pequena e focada.

Se for necessário alterar múltiplos arquivos, cada alteração deve ter relação direta com a causa encontrada.

Ao terminar, explicar:

1. qual era a causa raiz;
2. qual fluxo estava duplicando;
3. por que o bug só aparecia claramente com várias units;
4. quais arquivos foram alterados;
5. quais invariantes passaram a ser garantidas;
6. quais testes foram executados.
