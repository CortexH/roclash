# 🐛 Bug: MovementPlanning ignora parede posicionada na borda da célula

## ID
002

## Contexto

O sistema de movimentação atualmente utiliza:

```text
MovementIntent
    ↓
MovementIntentAcceptedHandler
    ↓
UnitMovementPlanningEvent
```

O `MovementIntentAcceptedHandler` é responsável por calcular o caminho entre a posição atual da unit e o destino utilizando pathfinding (A*), identificando também estruturas que bloqueiam o caminho.

Quando uma estrutura bloqueia o caminho, ela deve aparecer no `path` como `blocker`.

O problema identificado é que **paredes posicionadas na borda de uma célula não estão sendo identificadas pelo MovementPlanning**, mesmo quando estão diretamente entre a unit e seu destino.

---

## Reprodução

### Setup

1. Coloque uma **Tower** com behavior `Defensive`.
2. Coloque uma **Wall** diretamente entre a unit e a torre.
3. A parede deve estar posicionada na borda da célula da torre.
4. Coloque uma unit em uma célula alinhada verticalmente com a torre.
5. Mande explicitamente a unit **atacar a torre**.

A configuração espacial é essencialmente:

```text
X → Torre
- → Parede
* → Unit
```

Ou, visualmente:

```text
* - X
```

Onde:

* `*` = Unit
* `-` = Wall
* `X` = Tower

A unit está diretamente alinhada com a torre e existe uma parede entre as duas.

---

## Comportamento esperado

O `MovementIntentAcceptedHandler` deveria detectar que existe uma parede bloqueando o caminho até a torre.

O `UnitMovementPlanningEvent` deveria conter algo equivalente a:

```lua
["path"] = {
    {
        ["fromCell"] = ...,
        ["toCell"] = ...,
        ["blocker"] = "<wallId>"
    }
}
```

A unit deveria então:

1. Caminhar até a parede.
2. Identificar a parede como blocker.
3. Atacar/destruir a parede.
4. Após a alteração do mundo, realizar o fluxo de movimentação novamente.
5. Finalmente alcançar e atacar a torre.

O ponto importante é:

> A parede está fisicamente entre a unit e o destino e, portanto, deve ser reconhecida pelo planning como um blocker.

---

## Comportamento atual

O `MovementPlanning` está considerando o caminho como livre.

Em um dos testes, o `UnitMovementPlanningEvent` foi gerado assim:

```lua
["data"] = {
    ["path"] = {
        [1] = {
            ["fromCell"] = ...,
            ["toCell"] = ...
        }
    },
    ["reachable"] = true,
    ["startCell"] = ...,
    ["unitId"] = "99658abd-cbdc-41b2-8bed-22402f10a599"
}
```

Observe que o segmento do path **não possui `blocker`**.

Isso é incorreto, pois existe uma Wall diretamente entre a unit e a Tower.

Como consequência, a movimentação entende que o caminho até a torre está livre e a unit consegue chegar/atacar a torre sem primeiro resolver a parede.

---

## Evidência importante

O behavior da unit neste teste é:

```text
Defensive
```

Isso é importante porque `Defensive` significa que a unit **só deve atacar quando recebe uma ordem explícita**.

A unit recebeu explicitamente:

```text
Attack Tower
```

Portanto, o problema não deve ser interpretado como comportamento `Aggressive` escolhendo automaticamente uma entidade qualquer para atacar.

O problema observado ocorre **antes disso**, no planejamento do caminho.

---

# Hipótese inicial

A hipótese principal é que o `MovementIntentAcceptedHandler` / algoritmo de pathfinding está tratando a célula como livre sem considerar corretamente uma Wall posicionada na **borda da célula**.

A estrutura possui uma característica importante:

> A Wall pode ocupar a mesma célula que uma Tower, funcionando como uma borda/barreira entre a Tower e as células adjacentes.

Portanto, não necessariamente existe uma célula "ocupada pela parede".

A parede pode estar representando uma **barreira entre duas células**.

Exemplo:

```text
┌─────┬─────┐
│     │     │
│ *   │  X  │
│     │  T  │
└─────┴─────┘
        ↑
       Wall
```

A investigação deve verificar se o pathfinding está considerando corretamente esse tipo de estrutura.

---

# O que investigar

Não assumir imediatamente que o A* em si está incorreto.

Investigar todo o fluxo responsável por transformar o `MovementIntent` em `UnitMovementPlanningEvent`.

Principalmente:

### 1. Como Walls são representadas

Verificar:

* como a Wall é armazenada;
* como sua posição é representada;
* se ela possui informação de qual borda/lado da célula ocupa;
* como o sistema identifica Walls nas células;
* como o pathfinding consulta essas informações.

### 2. Como o A* avalia uma transição entre células

Verificar se o pathfinding considera apenas:

```text
"essa célula está ocupada?"
```

ou se também considera:

```text
"existe uma barreira entre a célula atual e a próxima célula?"
```

Isso é especialmente importante porque Walls podem coexistir com outras estruturas na mesma célula.

### 3. Como o `blocker` é descoberto

Identificar exatamente onde o valor:

```lua
blocker = ...
```

é produzido.

Determinar por que, neste cenário, ele está sendo omitido.

### 4. Verificar o caso vertical

Reproduzir especificamente:

```text
* - X
```

onde:

* a unit está em uma célula;
* a Wall está diretamente à frente;
* a Tower está atrás da Wall;
* todas estão alinhadas verticalmente.

Confirmar em qual etapa a Wall deixa de ser considerada.

### 5. Verificar casos diagonais

Depois de entender o caso vertical, verificar se a mesma lógica funciona quando a unit precisa atravessar uma transição diagonal próxima a uma Wall.

Não implementar uma solução específica apenas para o caso vertical se isso revelar um problema mais geral na representação de blockers.

---

# Não fazer

Não corrigir o problema simplesmente adicionando uma regra especial para:

```text
Unit → Wall → Tower
```

O objetivo é encontrar a causa real pela qual o planning não identifica uma estrutura que bloqueia o caminho.

Também não alterar a regra de targeting/aggro como primeira tentativa.

Neste caso a unit recebeu explicitamente a ordem de atacar a Tower e o problema observado já pode ser identificado no próprio `UnitMovementPlanningEvent`, onde o blocker está ausente.

---

# Critérios de aceite

* [ ] Uma Wall posicionada diretamente entre uma unit e seu destino é identificada pelo MovementPlanning.
* [ ] O `UnitMovementPlanningEvent` contém o ID da Wall no `blocker` correspondente.
* [ ] A unit não considera a Tower diretamente alcançável enquanto a Wall continuar bloqueando o caminho.
* [ ] O comportamento continua funcionando quando não existe Wall.
* [ ] O comportamento não depende do behavior `Aggressive`.
* [ ] O caso `Defensive Unit → Attack Tower → Wall → Tower` funciona corretamente.
* [ ] A solução considera corretamente Walls posicionadas nas bordas das células.
* [ ] Casos diagonais não são quebrados pela correção.
* [ ] Não foi criada uma regra específica/hardcoded para o cenário deste bug.
* [ ] O restante do sistema de MovementPlanning continua funcionando como antes.

---

# Resultado esperado

Para o cenário:

```text
* - X
```

o planejamento deve reconhecer:

```text
Unit
  ↓
Wall (blocker)
  ↓
Tower
```

e não:

```text
Unit
  ↓
Tower
```

A responsabilidade do planning é apenas identificar o obstáculo.

Ele **não precisa decidir o que fazer com a Wall**.

O resultado esperado do planning é simplesmente informar:

```lua
blocker = "<wallId>"
```

e deixar o restante do fluxo decidir como resolver esse obstáculo.
