# Bug — Unit para de atacar após troca manual de alvo durante combate

## Objetivo

Investigar e corrigir um bug no fluxo de combate em que uma unit que já está atacando um alvo recebe um novo comando de aggro durante o ataque, chega corretamente ao novo alvo e emite `TargetAcquiredEvent`, mas não inicia o ataque contra esse novo alvo.

A correção deve preservar o fluxo atual de combate e corrigir a causa raiz da interrupção.

---

## Cenário para reproduzir

1. Spawnar uma unit com comportamento `DEFENSIVE`.
2. Solicitar que ela ataque uma parede/estrutura.
3. A unit deve iniciar o aggro e continuar atacando as estruturas normalmente.
4. Enquanto ela estiver no meio de um ataque, solicitar que ela ataque outra unit.
5. A unit deve trocar o alvo, movimentar-se até ele e iniciar o ataque.
6. Atualmente, ela chega ao novo alvo, emite `TargetAcquiredEvent`, mas não continua o pipeline de ataque.

---

## Comportamento atual

O fluxo problemático observado é aproximadamente:

```text
UnitAggroCommand
    ↓
UnitAggroIntentEvent
    ↓
AggroIntentAccepted
    ↓
UnitAggroStartedEvent
    ↓
MovementIntent
    ↓
MovementIntentAccepted
    ↓
UnitMovementPlanningEvent
    ↓
UnitMovementStartedEvent
    ↓
UnitMovementResolvedEvent
    ↓
VerifyAggroReachedEvent
    ↓
TargetAcquiredEvent
    ↓
[FIM]
```

Depois de `TargetAcquiredEvent`, não é emitido:

```text
AttackIntent
AttackIntentAccepted
AttackStartedEvent
```

O problema, portanto, **não aparenta ser um `AttackIntent` rejeitado** nesse ponto. O `AttackIntent` sequer é produzido.

## Contexto importante

O novo `UnitAggroCommand` pode acontecer enquanto a unit ainda está executando um ataque anterior.

No caso observado:

```text
17:41:41.778 AttackStartedEvent
17:41:41.993 UnitAggroCommand
17:41:42.076 AttackImpactEvent
17:41:42.376 AttackResolvedEvent
```

Ou seja, o aggro foi alterado aproximadamente 215ms depois do início do ataque anterior, antes de seu `AttackResolvedEvent`.

A investigação deve considerar que existe uma transição de alvo enquanto o pipeline de ataque anterior ainda está em andamento.

# Código atualmente envolvido

O handler de `TargetAcquiredEvent` atualmente possui esta estrutura:

```lua
function module.handle(event : combatEventTypes.targetAcquiredEvent, context)
	if event.isValid == false then return {} end

	local selfView = viewPort.getSelfBattleView(event.data.unitId, context)
	if not selfView then return {} end
	if not selfView.canAttack then return {} end

	local brain = brainPort.getNpcBrain(event.data.unitId, context)
	if not brain then return {} end
	
	if not brain:getTargeting():isActiveTarget(event.data.targetId) then return {} end
	
	local intent : attackIntentTypes.AttackIntent = {
		delay = 0,
		eventType = "AttackIntent",
		type = "EVENT",
		data = {
			source = event.data.unitId,
			target = {
				targetType = "UNIT",
				id = event.data.targetId,
				position = {x = 0, y = 0}
			},
			origin = {
				type = "SYSTEM",
				playerId = nil
			}
		},
		isValid = true
	}

	return { intent }
end
```

---

# Principal suspeita

Existe uma validação especialmente importante:

```lua
if not brain:getTargeting():isActiveTarget(event.data.targetId) then
	return {}
end
```

Essa validação pode estar impedindo silenciosamente a criação do `AttackIntent`.

Entretanto, **não assuma que essa é a causa raiz**.

Investigue primeiro.

O fato relevante é:

```text
TargetAcquiredEvent
        ↓
handler
        ↓
nenhum AttackIntent
```

O handler possui múltiplos `return {}` antecipados. Qualquer um deles pode estar interrompendo o fluxo.

---

# Investigação obrigatória

Antes de alterar comportamento, rastrear:

### 1. Todos os consumidores de `TargetAcquiredEvent`

Descobrir:

* onde o evento é produzido;
* onde é consumido;
* qual handler é responsável por gerar `AttackIntent`;
* quais validações são executadas antes disso.

### 2. Todos os estados consultados pelo handler

Investigar especificamente:

```lua
selfView.canAttack
```

e:

```lua
brain:getTargeting():isActiveTarget(event.data.targetId)
```

Determinar:

* o que `canAttack` representa;
* como ele é atualizado;
* o que `isActiveTarget()` considera como "active target";
* quando o active target é alterado;
* se a troca de aggro atualiza esse estado;
* se existe diferença entre `aggroTargetId` e `targeting.activeTarget`.

### 3. Ordem dos eventos durante a troca

Rastrear o estado da unit nesta sequência:

```text
Ataque contra alvo A
        ↓
UnitAggroCommand para alvo B
        ↓
Aggro atualizado
        ↓
Ataque A finaliza
        ↓
Movimento até B
        ↓
TargetAcquired(B)
        ↓
AttackIntent(B)
```

Verificar se algum evento do ataque anterior modifica ou invalida o estado necessário para atacar B.

### 4. Eventos atrasados/antigos

Verificar se eventos relacionados ao ataque anterior podem estar sendo processados depois da troca de alvo e alterando:

* target;
* aggro;
* targeting;
* attack state;
* cooldown;
* versões/generation;
* qualquer estado utilizado por `TargetAcquiredEvent`.

# Instrumentação temporária

Durante a investigação, adicionar logs temporários ao handler de `TargetAcquiredEvent` para identificar exatamente qual guard está interrompendo o fluxo.

Exemplo conceitual:

```lua
print("[TargetAcquired] Attack check", {
	unitId = event.data.unitId,
	targetId = event.data.targetId,
})
```

Cada saída antecipada deve poder ser identificada separadamente:

```text
BLOCKED: invalid event
BLOCKED: no self view
BLOCKED: cannot attack
BLOCKED: no brain
BLOCKED: target is not active
```

Também registrar, quando relevante, o estado de targeting/aggro necessário para entender a divergência.

**Os logs são ferramentas de investigação. Não devem permanecer no código final caso sejam apenas instrumentação temporária.**

# Hipótese que deve ser validada

Uma possibilidade é:

```text
Unit está atacando A
        ↓
Player manda atacar B
        ↓
Aggro muda para B
        ↓
Ataque anterior ainda possui eventos pendentes
        ↓
Estado de targeting/attack é alterado
        ↓
Unit chega em B
        ↓
TargetAcquired(B)
        ↓
isActiveTarget(B) == false
        ↓
AttackIntent não é criado
```

Outra possibilidade é um dos demais guards do handler impedir a criação do intent.

Não implementar a hipótese sem verificar o estado real.

---

# Critérios de aceitação

A correção está concluída quando:

### Caso principal

Uma unit que está atacando A pode receber:

```text
UnitAggroCommand(B)
```

durante o ataque e posteriormente:

```text
TargetAcquired(B)
AttackIntent(B)
AttackIntentAccepted(B)
AttackStartedEvent(B)
```

sem ficar travada.

### Continuidade

Depois de atacar B, a unit deve continuar seguindo o comportamento esperado do seu aggro/AI.

### Ataques normais

O fluxo existente de ataque não pode ser quebrado:

```text
TargetAcquired
→ AttackIntent
→ AttackIntentAccepted
→ AttackStarted
→ AttackImpact
→ DamageApplied
→ AttackResolved
→ CooldownReady
→ próximo AttackIntent
```

### Eventos obsoletos

Eventos relacionados ao alvo anterior não devem conseguir corromper o estado do novo alvo.

### Validações

Não remover validações existentes simplesmente para fazer o ataque funcionar.

Se uma validação estiver incorreta, corrigir sua semântica/estado na origem.

### Escopo

Não realizar refatorações arquiteturais amplas.

Alterar somente o necessário para corrigir a causa raiz.

---

# Testes obrigatórios

Validar pelo menos:

1. **Ataque normal**

   * Unit ataca uma estrutura.
   * Continua atacando normalmente.

2. **Troca de alvo durante ataque**

   * Unit ataca A.
   * Durante o ataque, recebe comando para atacar B.
   * Unit chega em B.
   * `TargetAcquired(B)` gera `AttackIntent(B)`.
   * Unit ataca B.

3. **Troca de alvo após ataque**

   * Unit termina o ataque em A.
   * Depois recebe comando para B.
   * Deve funcionar normalmente.

4. **Múltiplas trocas**

   * A → B → C durante a execução dos ataques.
   * Apenas o alvo vigente deve controlar o comportamento atual.

5. **Alvo inválido/morto**

   * O comportamento existente de invalidação deve continuar funcionando.

6. **Cooldown**

   * A troca de alvo não pode criar ataques duplicados ou ignorar o controle de cooldown.

---

# Restrições

* Não remover `isActiveTarget()` sem entender por que ele existe.
* Não gerar `AttackStartedEvent` diretamente a partir de `TargetAcquiredEvent`.
* Manter `TargetAcquiredEvent → AttackIntent` como fluxo conceitual.
* Não fazer o `TargetAcquiredEvent` modificar diretamente o estado da Unit.
* Não introduzir estado duplicado apenas para contornar o bug.
* Não mascarar o problema com delays arbitrários.
* Não alterar o comportamento de outras partes do sistema sem necessidade.

---

# Resultado esperado

Ao final, o agente deve conseguir explicar claramente:

1. **Qual condição fazia o `TargetAcquiredEvent` não gerar `AttackIntent`;**
2. **Por que essa condição ocorria especificamente durante a troca de alvo enquanto a unit estava atacando;**
3. **Qual estado/evento estava inconsistente ou obsoleto;**
4. **Qual foi a menor correção necessária;**
5. **Quais testes foram realizados para garantir que o problema não voltou.**

A correção deve ser baseada na causa raiz encontrada, e não apenas no sintoma de que o `AttackIntent` não estava sendo criado.
